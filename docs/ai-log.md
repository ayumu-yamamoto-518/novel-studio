# AIログ

AIの出力が間違っていた場合や、人が直した場合の記録。

- 実際に起きたことだけを書く。
- 人が「記録して」と言ったときに下書きを作り、人が確認してから保存する。

## テンプレート

新しい記録は、この下に新しい順で追加する。

```markdown
### YYYY-MM-DD タイトル

- **何が起きたか**:
- **どう気づいたか**:
- **どう直したか**:
- **学び**:
```

### 2026-11-01 テストだけを回して緑を信じ、型エラーが `npm run check` で初めて見つかった

- **何が起きたか**: 保存の応答を保留にする偽のハンドラを書いたとき、`request.json()` の結果を `{ body: string }` の型で受けた。MSW では `request.json()` は `DefaultBodyType` を返すため、型が合わなかった(TS2322)。Vitest は型を検査しないので、テストは緑で、続けて行った2つのミューテーションも、期待どおりに赤になった。
- **どう気づいたか**: ミューテーションまで終えたあと、最後に `npm run check` を回すと、型検査で失敗した。
- **どう直したか**: 受け取った値を `unknown` として、本文が文字列であることを確かめてから使う形にした(`any` も `as` も使わない)。直したあとに、ミューテーションを再実行して、結果が変わらないことを確かめた(7864375)。
- **学び**: テストの緑は、型検査の緑ではない。テストを足したら、ミューテーションに入る前に `npm run typecheck` も回す。

### 2026-11-01 編集中の再取得の失敗で、下書きが失われる設計だった

- **何が起きたか**: 本文エディタは、取得の失敗(`isError`)や章が無い(`null`)かどうかを、章の表示より先に判定していた。本番の QueryClient は既定値のままで、タブに戻ると(ウィンドウのフォーカス復帰)データを取り直す。そのため、本文を入力中に取り直しが失敗すると、エディタが「章を読み込めませんでした」に変わり、未保存の下書きが確認なしで失われる設計だった。別のタブで章が削除されていた場合も同じで、別のタブで同じ章が保存されていると、触っていないのに「未保存」と出た。
- **どう気づいたか**: PR前の別 AI レビューが、TanStack Query の実装を読んで指摘した(Important)。Claude Code の側では、設計の時点で、既定の再取得が編集中の画面に与える影響を考えていなかった。レビューの推論は、再現するテストを先に書いて、3件が赤になることを確かめた。
- **どう直したか**: `useChapter` に `staleTime: Infinity` を付け、タブに戻っても取り直さないようにした(d988d5b)。`staleTime` を外すと、3件が赤になる。別のタブでの保存は「最後に保存したほうが勝つ」ことを、README の既知の課題に書いた(512bdbe)。ブラウザでの確認(タブを離れて戻る)でも、本文は消えなかった。
- **学び**: 編集中の画面は、取得の状態の変化(失敗、削除、更新)に引きずられて消えない設計にする。ライブラリの既定の再取得が、入力中の状態に何をするかを、設計の時点で考える。

### 2026-11-01 「保存の応答を待つ間に書き足す」場面のテストが抜けていた

- **何が起きたか**: 保存中は保存ボタンが無効になることを確かめるため、保存の応答を保留にする仕組みを作った。しかし、その保留の間に本文を書き足したときの動きを確かめるテストは、足していなかった。将来「保存に成功したら、下書きを応答の本文で置き換える」変更が入ると、書き足した本文が静かに消えても、全テストが通る状態だった。
- **どう気づいたか**: 計画を確認していた別の AI(チャット側)の指摘を受けて、人が「保留の間に書き足すテストは入っていますか」と尋ねた。尋ねられてテストを確認し、入っていないことに気づいた。自分のテスト一覧の棚卸しでは、気づいていなかった。
- **どう直したか**: 2件を足した(7864375)。(1) 1回目の保存の応答を保留にし、その間に書き足し、応答のあとも書き足した分が残り、もう一度保存すると保存される。(2) 保存が済んだあとに書き足して、もう一度保存すると保存される。どちらも最初から緑で、実装が正しかったことは、コードを読んだ推論どおりだった。緑のまま信用せず、実装を2つ壊した(保存成功時に下書きを応答の本文で置き換える、成功後に無条件で「保存済み」と表示する)。壊し方が適用されたことを差分で確かめたうえで、それぞれ1件、2件が失敗した。
- **学び**: 非同期の途中の状態を作る仕組み(応答の保留)を作ったら、「その間に状態が変わる」場面まで、テストの一覧に入れる。保存中×入力のように、状態の組み合わせを表にして棚卸しする。

- **学び**: 権限ルールの効く範囲は、記憶や推測で書かず、公式ドキュメントの記述と実際の拒否で確かめる。

### 2026-11-01 git の許可ルールが、任意ファイルの書き込み・読み取りを確認なしで通した

- **何が起きたか**: `.claude/settings.json` の allow に `git diff *`・`git log *`・`git show *` を「読み取り専用」として入れた。しかし `git diff` は `--output=<ファイル>` で任意のパスに書き込め、`--no-index` で範囲外のファイルを読めた。
- **確認できたこと**: 上の2点は、レビュアーが実際にコマンドを実行して確認した。ask に入れた旧パターン `git diff --no-index *` は、`--no-index` の前に別のオプションが入ると一致せず、`git diff --stat --no-index a b` が確認なしで実行されることを、このセッションで実際に確かめた。
- **どう気づいたか**: 全ブランチのレビュー(別コンテキストのレビュアー)が指摘した。Claude Code は名前から読み取り専用と思い込み、実行して確かめていなかった。
- **どう直したか**: ask に `Bash(git diff --no-index *)` と `Bash(git * --output*)` を追加し(6524f1d)、のちに `--no-index` のパターンを位置を問わない `Bash(git diff *--no-index*)` に直した(bfeeb14)。このプロジェクトではどちらのオプションも使わないため、最終的に2つとも ask から deny に移した(b8d0545)。
- **直したあとに確認できたこと**: 新しい場所(~/Developer/novel-studio)で、deny に移したあとに `git diff --stat --no-index .nvmrc .prettierrc` を単独で実行すると、拒否された。以前は確認なしで実行された同じコマンドなので、`Bash(git diff *--no-index*)` は `--no-index` の前にオプションがあっても効いている。ask のときに確認が出なかった理由(権限モードで省略されていたのか、ルールが効いていなかったのか)は、deny にしたため切り分けていない。同じく、`git diff --output=/private/tmp/diffout-test.txt .nvmrc` を単独で実行すると拒否され、出力先のファイルは作られなかった。`Bash(git * --output*)` も効いている。
- **まだ確認していないこと**: deny に移したあとのコミットコマンドが、メッセージ本文に `--no-index` と `--output` を含んでいたために拒否された。パターンはコマンド全体の文字列に一致するようなので、本文に書いただけでも拒否されると考えられるが、どちらのパターンに一致したかは切り分けていない。コミットメッセージはファイル経由(`git commit -F`)で渡して回避した。
- **学び**: 「読み取り系」と名前だけで決めず、オプションの組み合わせを実際に試す。ルールを直したあとは、そのコマンドが止まることまで確かめる。

### 2026-11-01 基本設定の ESLint では、eslint-disable コメントで any を隠せた
