# AIログ

AIの出力が間違っていた場合や、人が直した場合の記録。

- 実際に起きたことだけを書く。
- 人が「記録して」と言ったときに下書きを作り、人が確認してから保存する。

## テンプレート

新しい記録は、この下に新しい順で追加する。

```markdown
### YYYY-MM-DD タイトル

- **何が起きたか**:
- **どう気づいたか**:
- **どう直したか**:
- **学び**:
```

### 2026-11-01 操作中の無効化が未検証で、状態の漏れを検出するテストが順序依存だった

- **何が起きたか**: PR前の別 AI レビューで2点が指摘された。(1) 「変更・削除中は全行のボタンを `disabled` にする」実装(`isBusy`)を確かめるテストが1本もなく、`disabled` を外しても全テストが通る。ダブルクリックのテストは、同じ値の PATCH や 404 の成功扱いで結果が変わらないため、`disabled` と無関係に通っていた。(2) jotai の store が render ごとに分かれていることを確かめるテストが、直前のテストが「完了」タブを選んだまま終わることに頼っていた。並べ替えると、赤にならず無言で緑のままになる形だった。
- **どう気づいたか**: レビュアーが、`grep` で `disabled` がテストコードに無いことと、テストの順序依存を指摘した。Claude Code の側では、自分で書いたテストを、守りたい実装ごとに壊して確かめる手順が、`isBusy` と順序依存の分には回っていなかった。
- **どう直したか**: 応答を保留にして操作が進行中の状態を作り、ほかの行のボタンが無効になることを確かめる2件を追加した(4d8fe24)。漏れの検出テストは、1つのテストの中で完結する形にし、単独で実行しても Provider の欠落を検出できることを確認した(fa906ce)。
- **学び**: 実装した分岐ごとに、「壊したら赤になるテスト」が対応しているかを棚卸しする。他のテストの終わり方に頼るテストは、順序を変えると何も検出しなくなる。

### 2026-11-01 コミットメッセージ用ファイルのパスを書き間違え、意味のないファイルを作ろうとした(PR1・PR2・PR4 で計4回、うち2回は実際に作られた)

- **何が起きたか**: コミットメッセージを書くファイルのパスを、scratchpad ではない誤ったパス(`-Users-<ユーザー名>/-Developer-…`)で書いた。(1) PR1 では誤ったディレクトリが実際に作られた。(2) PR2 の作業中に、同じ誤ったパスへ中身が `x` だけのファイルを書こうとして、2回とも人に拒否された。(3) 「作らないでください」と指摘された後の PR4 で、また同じパスに `x` を書き、今度は拒否されずに作られた。
- **どう気づいたか**: (1) は自分で気づいて削除した。(2) は書き込みの許可を求められた人が拒否した。(3) は書き込みが成功したあとに自分で気づき、中身が自分の `x` だけであることを確認してから削除した。
- **どう直したか**: 誤ったディレクトリを削除し、以後は、正しい scratchpad の絶対パスをコピーして使うことにした。コミットの前に、誤ったパスのディレクトリが存在しないことを `ls` で確認している。
- **学び**: 長いパスを毎回手で組み立てると、同じ間違いを指摘のあとにも繰り返す。目的のない書き込みは、許可を求める前に自分で止める。

### 2026-11-01 「壊して赤を確かめる」試みが、型エラー・構文エラーで成立していなかった

- **何が起きたか**: ミューテーション(わざと実装を壊してテストが落ちることを確かめる作業)で、2回、壊し方が不正で、テストが実行されなかった。(1) 不正な `status` を通すため `sed` で条件を `false` に置き換えたら、型エラーになりテストまで届かなかった。(2) タブを切り替えなくするため式の位置に文を書いたら、構文エラーで `no tests` になった。
- **どう気づいたか**: (1) は `tsc` のエラー出力が出て、テストの結果が出ていなかった。(2) は `Tests no tests` と表示された。どちらも「赤になった」ではなく、「テストが実行されていない」ことに気づけた。
- **どう直したか**: 型と構文が通る形(`as` を使う、`() => setStatus('writing')` にする)に直して、やり直した(ac17042、a4a506f)。コミットメッセージにも、最初の試みが成立していなかったことを書いた。
- **学び**: ミューテーションは、「テストが失敗した」ことまで確かめてはじめて成立する。出力に失敗したテスト名が出ているかを見る。

### 2026-11-01 削除のテストが、エラーが描画されない構造のせいで空振りしていた

- **何が起きたか**: 「404 は成功として扱う」ことを確かめるテストが、その実装を外しても緑のままだった。作品が1件だけのテストだと、削除後に一覧が空になり、`WorkList` が「作品がありません」だけを描画するため、削除エラーの `alert` が出ない。「エラーが出ていない」というアサーションが、実装と無関係に成立していた。
- **どう気づいたか**: PR2 の二重送信の件の学びに従い、404 の扱いを外すミューテーションを試した。`invalidate` を外すミューテーションは赤になったが、こちらは緑のままだった。
- **どう直したか**: 別の作品を1件残す形にして、エラーがあれば描画される状況にした。404 の扱いを戻すと2件が失敗することを確かめた(3e0a1dd)。
- **学び**: 「〜が出ていない」を確かめるテストは、実装が壊れていれば実際に出る状況を作らないと空振りする。ミューテーションは、守りたい分岐ごとに試す。

### 2026-11-01 db の「壊れたデータは空として扱う」という説明が、実装と食い違っていた

- **何が起きたか**: `readDb` のコミットメッセージに「想定外の形のデータは空の DB として扱う」と書いたが、実装は `works` が配列かどうかしか見ていなかった。要素が `null` や形の違うオブジェクトだと、そのまま画面に渡り、一覧画面全体が落ちる状態だった。
- **どう気づいたか**: PR前の別 AI レビューで、`{"works":[null]}` で `work.id` が TypeError になる、と指摘された(Important)。`Array.isArray` を通ると `any[]` になり、型チェックを素通りしていた。
- **どう直したか**: 失敗するテストを先に書いて赤を確認し、要素ごとに `Work` の形を確かめて、壊れた要素だけ捨てるようにした(a560b6e)。DB 全体を空にすると、次の作成で有効な作品まで消えるため、この方針にした。
- **学び**: 「想定外のデータに強い」と書くなら、想定外の入力をテストで実際に試す。`any` が型検査をすり抜ける場所(`Array.isArray` の後など)に注意する。

### 2026-11-01 二重送信のテストが、ガードを外しても通る偽の緑だった

- **何が起きたか**: 作成フォームの二重送信を防ぐ `disabled={isPending}` に対して、`dblClick` で作品が1件だけ作られることを確かめるテストを書き、緑になった。しかし `disabled` を外しても緑のままだった。
- **どう気づいたか**: 緑を信用せず、実装を壊して赤になるか確かめた。原因は3つあった。(1) `readDb()` が、2回目の保存前の時点を見ていた。(2) user-event は操作の間に待ちを挟むため、その間に MSW の応答が返り、ガードの有無と無関係な結果になっていた。(3) `isPending` の反映は1拍遅れ、応答前の2回目のクリックを防げていなかった。
- **どう直したか**: POST の送信回数を `server.events` で直接数え、`userEvent.setup({ delay: null })` で応答前に2回目のクリックが来る状況にした。ref による同期的なガードを足し、ref を外すと失敗することを確かめた(019fe47)。
- **学び**: テストが緑でも、守りたい実装を壊して赤になることを確かめるまで信用しない。非同期の状態(`isPending`)は反映が遅れるので、送信回数のような直接の証拠で見る。

### 2026-11-01 「Read(.env) の拒否は Bash の cat を止めない」と記録したが、公式ドキュメントと食い違っていた

- **何が起きたか**: 権限設定の `Read(./.env)` について、「Bash の `cat` は止めない」と作業メモと報告に書いた。実際に試したものではなかった。公式ドキュメントでは、Read の拒否ルールは `cat`・`head`・`tail`・`sed`・`tee` とリダイレクト先にも適用され、止まらないのは、ファイル名を指定しない `grep -r` や、Python/Node のスクリプトがファイルを直接開く場合と書かれている。
- **どう気づいたか**: docs/ai-log.md に限界として記録する際に、根拠を公式ドキュメント(https://code.claude.com/docs/en/permissions)で確認し直した。このセッションでも、`cat .env` を含むコマンドは拒否され、`.env` を Write で作ることも拒否された(`cat` 単独では確認できていない)。
- **どう直したか**: 記録を正しい限界(`grep -r` とスクリプト経由は止まらない)に直した。技術的には塞がず、人の許可と、`.env` に秘密情報を置かない運用で補う。
- **学び**: 権限ルールの効く範囲は、記憶や推測で書かず、公式ドキュメントの記述と実際の拒否で確かめる。

### 2026-11-01 git の許可ルールが、任意ファイルの書き込み・読み取りを確認なしで通した

- **何が起きたか**: `.claude/settings.json` の allow に `git diff *`・`git log *`・`git show *` を「読み取り専用」として入れた。しかし `git diff` は `--output=<ファイル>` で任意のパスに書き込め、`--no-index` で範囲外のファイルを読めた。
- **確認できたこと**: 上の2点は、レビュアーが実際にコマンドを実行して確認した。ask に入れた旧パターン `git diff --no-index *` は、`--no-index` の前に別のオプションが入ると一致せず、`git diff --stat --no-index a b` が確認なしで実行されることを、このセッションで実際に確かめた。
- **どう気づいたか**: 全ブランチのレビュー(別コンテキストのレビュアー)が指摘した。Claude Code は名前から読み取り専用と思い込み、実行して確かめていなかった。
- **どう直したか**: ask に `Bash(git diff --no-index *)` と `Bash(git * --output*)` を追加し(6524f1d)、のちに `--no-index` のパターンを位置を問わない `Bash(git diff *--no-index*)` に直した(bfeeb14)。このプロジェクトではどちらのオプションも使わないため、最終的に2つとも ask から deny に移した(b8d0545)。
- **直したあとに確認できたこと**: 新しい場所(~/Developer/novel-studio)で、deny に移したあとに `git diff --stat --no-index .nvmrc .prettierrc` を単独で実行すると、拒否された。以前は確認なしで実行された同じコマンドなので、`Bash(git diff *--no-index*)` は `--no-index` の前にオプションがあっても効いている。ask のときに確認が出なかった理由(権限モードで省略されていたのか、ルールが効いていなかったのか)は、deny にしたため切り分けていない。同じく、`git diff --output=/private/tmp/diffout-test.txt .nvmrc` を単独で実行すると拒否され、出力先のファイルは作られなかった。`Bash(git * --output*)` も効いている。
- **まだ確認していないこと**: deny に移したあとのコミットコマンドが、メッセージ本文に `--no-index` と `--output` を含んでいたために拒否された。パターンはコマンド全体の文字列に一致するようなので、本文に書いただけでも拒否されると考えられるが、どちらのパターンに一致したかは切り分けていない。コミットメッセージはファイル経由(`git commit -F`)で渡して回避した。
- **学び**: 「読み取り系」と名前だけで決めず、オプションの組み合わせを実際に試す。ルールを直したあとは、そのコマンドが止まることまで確かめる。

### 2026-11-01 基本設定の ESLint では、eslint-disable コメントで any を隠せた
